# E4 — Бизнес-слой (CRM + Kanban)

> **Статус:** план-спек (далёкая фаза; **БЛОКИРОВАН сбором требований** по смыслу «CRM» для гос-заказчика). Greenfield.
> **Источники:** мастер-план §4 (E4), [ROADMAP.md](../../ROADMAP.md), ADR [D-004](../../ARCHITECTURE_DECISIONS.md), [D-005](../../ARCHITECTURE_DECISIONS.md), [D-007](../../ARCHITECTURE_DECISIONS.md) (RBAC/scoping).

---

## ⚠️ Предусловие (критично)

> **«CRM» для B2G размыт** (мастер-план §4, риск E4). До дизайна доменных сущностей **обязателен сбор требований** у заказчика: что именно подразумевается под «CRM»?
> Гипотезы: обращения граждан · поручения (топ→низ по иерархии) · задачи/тикеты · документооборот-lite · контакты контрагентов.
> **Этот спек фиксирует каркас Kanban (он определён) и помечает CRM как требующий уточнения.** Доменная модель CRM ниже — предварительная, подлежит замене после требований.

---

## Цель

Бизнес-слой поверх ядра: **Kanban-доска** (визуальное управление задачами/поручениями drag-drop) + **CRM-сущности** (после уточнения смысла). Связь с встречами и сотрудниками. Закрывает пункт ТЗ «CRM + KANBAN».

---

## Scope (пункты ТЗ → задачи)

- **Kanban-доска** (LiveView): колонки (настраиваемые статусы), карточки, **drag-drop** перемещение, назначение исполнителя, приоритет, дедлайн.
- **CRM-сущности** *(зависят от требований)*: сущность-«запись» (обращение/поручение/задача), история, связи с пользователями и встречами.
- **Связь с ядром:** карточка/запись ↔ встреча (E2) и сотрудник (E0); создание поручения из встречи; обсуждение записи → планирование встречи (E3).
- **RBAC-scoping** ([D-007]): видимость досок/записей по департамент-иерархии (Manager — своё поддерево).
- **Аудит:** изменения статусов/назначений/записей → `audit_logs`.

---

## Ключевые задачи

1. **Kanban LiveView + drag-drop:** колонки/карточки, JS hook (SortableJS-класс библиотека — проверить через Context7) → событие в LiveView → пере-сортировка `position`, оптимистичный UI, live-sync через PubSub (несколько пользователей на одной доске).
2. **Board/Column/Card context** (`svc_core`): `Boards` — CRUD досок, колонок, карточек; упорядочивание (lexorank/float `position`); права.
3. **CRM context** *(после требований)*: сущности обращений/поручений/задач, статусная машина, история изменений (audit-trail на сущность), вложения (опц.).
4. **Интеграции:** «создать поручение из встречи», «запланировать встречу по записи» (мост к E3), «привязать сотрудника-исполнителя» (E0).
5. **Фильтры/поиск/представления:** по исполнителю, статусу, дедлайну, департаменту; swimlanes (опц.).
6. **Уведомления:** назначение/смена статуса/приближение дедлайна → через Notification-каналы E3.

## Технический подход

- **Стек:** чистый **Phoenix LiveView** ([D-004]) — без отдельного SPA; drag-drop через JS hook + минимальная клиентская библиотека сортировки (выбор/версия — Context7 перед стартом, НЕ гадать).
- **Упорядочивание карточек:** дробный `position` (float) или lexorank-строки — избегать массового пересчёта при перемещении; ребалансировка по необходимости.
- **Конкурентность:** Phoenix PubSub — broadcast изменений доски всем подписчикам LiveView; разрешение конфликтов перемещений (last-write + reorder).
- **CRM:** **отложить детальный дизайн** до требований; заложить generic-каркас (полиморфная «запись» со статусной машиной), чтобы не переписывать ядро.
- **Связи с встречами/сотрудниками:** FK на `meetings`/`users`; переиспользовать RBAC-scoping E0/E2.

## Предварительные доменные сущности (Ecto)

> **Kanban — относительно стабилен. CRM — ЗАГЛУШКА до требований.** Все таблицы несут `org_id` ([D-005]).

**Kanban (определено):**
- **boards** `(id, org_id, name, description, owner_id, department_id?, visibility [private|department|org])`.
- **board_columns** `(id, org_id, board_id, name, position, wip_limit?)`.
- **cards** `(id, org_id, board_id, column_id, title, description, assignee_id?, reporter_id, priority [low|med|high|urgent], due_date?, position, status, meeting_id? [связь с E2], crm_record_id? [связь ниже])`.
- **card_activities** `(id, org_id, card_id, actor_user_id, action, from_value, to_value, inserted_at)` — история карточки.

**CRM (предварительно — заменить после требований):**
- **crm_records** `(id, org_id, type [обращение|поручение|задача|...], title, body, status, priority, requester_info jsonb, assigned_to?, source_meeting_id?, due_date, closed_at)` — generic-сущность; точные поля/типы зависят от значения «CRM».
- **crm_record_events** `(id, org_id, record_id, actor_user_id, kind, payload jsonb, inserted_at)` — audit-trail записи.

## Риски

- **🚩 Размытость «CRM» (главный риск, из мастер-плана):** без требований заказчика любой дизайн CRM = угадывание → переделка. **Сбор требований обязателен до Фазы 5.**
- **Drag-drop UX в LiveView:** latency сети при оптимистичном UI; конфликты одновременных перемещений; мобильный/тач (если web откроют на планшете).
- **Over-engineering:** generic-CRM-каркас может оказаться избыточным или недостаточным — балансировать после требований.
- **Объём:** при широкой трактовке «CRM» (полноценный документооборот/обращения граждан) эпик может разрастись в отдельный продукт — управлять scope.

---

## Зависимости

- **E0** (Фундамент) — orgs/users/RBAC/department-scoping/audit.
- *(связи, не блокеры)* **E2** — `meetings`/сотрудники для привязки карточек/записей.
- *(связь)* **E3** — каналы уведомлений (назначения/дедлайны), создание встречи из записи.
- **Внешнее:** требования заказчика по «CRM» — **жёсткий блокер дизайна**.

## Открытые вопросы

1. **🚩 Что есть «CRM» для гос?** Обращения граждан / поручения по вертикали / внутренние задачи / документооборот / контакты контрагентов? — определяет всю доменную модель.
2. **Источник записей CRM:** ручной ввод? интеграция с гос-системами (ЕПИГУ/обращения)? импорт?
3. **Kanban-доски:** персональные / департаментные / общеорганизационные? Кто создаёт колонки и настраивает workflow?
4. **Статусные машины:** фиксированные статусы или настраиваемые per-board/per-record-type?
5. **SLA/дедлайны:** есть ли регламентные сроки обработки обращений (гос-регламент) → автоэскалация?
6. **Связь Kanban↔CRM:** Kanban — это представление CRM-записей, или независимая сущность задач? (влияет на `cards.crm_record_id`).
7. **Вложения/документы:** нужны ли файлы на карточках/записях (storage, шифрование at-rest как у записей)?
