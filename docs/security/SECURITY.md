## 1. Контекст и философия

Система предназначена для государственного ведомства РУз: защищённая видеоконференцсвязь
плюс мониторинг присутствия и подлинности участников (face-match, liveness, анти-DeepFake).
Это **employer-monitoring**, а не zero-trust-мессенджер: сотрудники доверяют своему ведомству и
его on-prem инфраструктуре, но система защищается от внешних атак, инсайдеров и утечек.

**Foundation overkill (D-014, закон проекта).** Фундамент (E0) строится по-максимуму с дня 1:
полный сквозной audit-log, шифрование в каждом слое, серьёзный RBAC с иерархией, `org_id`-изоляция,
секреты вне git. Не MVP-урезка. Обоснование: фундамент держит всё, что строится сверху; для B2G
переделка основания дороже и опаснее, чем «overkill» сразу.

**Honest security (D-013).** Мы не обещаем заказчику недостижимого. Скриншот/запись экрана —
enforce только на Windows и Android, на macOS/iOS — детект, на web — невозможно (поэтому видео
вынесено из web, D-001). Звукозапись не блокируется нигде → forensic-watermark + трассировка.
Подробности и матрица — [anti-capture-matrix.md](anti-capture-matrix.md).

## 2. Модель угроз

### 2.1 Активы (что защищаем)

| Актив | Чувствительность | Где живёт | Ключевой риск |
|-------|------------------|-----------|---------------|
| **Видео/аудио совещаний** (живой поток) | Высокая (гос-совещания) | Клиент ↔ LiveKit (DTLS-SRTP), in-memory на SFU | Перехват канала, захват экрана/звука участником, MITM |
| **Записи совещаний** (at-rest) | Высокая | Object storage (S3-совм.), `meeting_recordings` | Кража файлов, доступ без RBAC, утечка ключей |
| **ПДн сотрудников** (Фото-эталон, ФИО, должность, департамент) | Высокая (ПДн + биометрия лица) | PostgreSQL, фото — app-level AES-256 | Утечка биометрии, нарушение закона о ПДн РУз |
| **Журналы посещаемости** (present/late/absent, кто-когда-входил) | Средняя/высокая (поведенческие данные о госслужащих) | PostgreSQL (`attendance_records`) | Подмена статусов, утечка, неавторизованный доступ менеджеров вне иерархии |
| **Audit-log** (действия, входы, изменения политик) | Высокая (целостность = доказуемость) | PostgreSQL (`audit_*`) | Подделка/удаление записей, заметание следов инсайдером |
| **Учётные данные** (пароли Argon2id, TOTP-секреты, сессии) | Критическая | PostgreSQL (хеши/секреты), session store | Кража хешей, обход 2FA, угон сессии |
| **Секреты системы** (LiveKit API key/secret, JWT-ключи, DB-креды, at-rest ключи) | Критическая | env / Vault (НЕ git) | Компрометация ключей → подделка JWT, доступ к медиа, расшифровка at-rest |
| **ML-результаты** (face-match score, liveness, deepfake-флаги) | Средняя | PostgreSQL | Манипуляция оценками подлинности, false-accept |

### 2.2 Акторы угроз

#### A. Внешний злоумышленник (без доступа)
**Цели:** перехват медиа, получение ПДн/записей, проникновение в контур.
**Векторы:** MITM на сигналинге/медиа, атака на публичные endpoint (web-админка, webhooks),
brute-force/credential-stuffing на вход, эксплуатация уязвимостей LiveKit/Phoenix, доступ из VPN/чужой
геолокации.
**Контроли:** TLS 1.2+ везде; DTLS-SRTP для медиа; rate-limit + Argon2id + TOTP; HMAC-подпись
webhooks (raw body до парсинга); on-prem (нет публичного облака); VPN/гео-детект (D-012); сетевая
сегментация; host-networking LiveKit без лишней внешней экспозиции.

#### B. Недобросовестный сотрудник (легитимный участник)
**Цели:** слить содержимое совещания (скриншот/запись экрана/звукозапись), обойти контроль присутствия.
**Векторы:** захват экрана сторонними инструментами (OBS/loopback), вторая физическая камера,
запись микрофона, подмена лица (фото/видео/DeepFake вместо себя), запуск с rooted/jailbroken-устройства.
**Контроли:** enforce анти-захвата (Win `setContentProtected`, Android `FLAG_SECURE`) + детект на
mac/iOS; **видимый per-user watermark** (ФИО+SessionID+timestamp) — психологический детеррент;
**forensic аудио-watermark** — трассировка утечки до пользователя; face-match + liveness + deepfake-flag
(D-011); risk-scoring root/jailbreak. **Фундаментально:** вторая камера и звукозапись не блокируются →
сдвиг «prevent → detect, identify, prosecute» (см. [anti-capture-matrix.md](anti-capture-matrix.md)).

#### C. Скомпрометированное устройство (доверенный пользователь, заражённая машина)
**Цели атакующего через устройство:** кража сессии/токенов, чтение медиа в памяти клиента, экфильтрация.
**Векторы:** malware крадёт session-cookie/JWT, screen-scraping в обход content-protection, кейлоггер,
скомпрометированный WebView2.
**Контроли:** короткий session-timeout; привязка/ротация JWT (короткоживущие LiveKit-токены, выдаются
per-join); Tauri Rust-shell для kiosk/TPM-проверок целостности (E5); детект рекордеров; минимизация
секретов на клиенте (клиент НЕ хранит долгоживущих ключей); audit входов с гео/устройством.
**Граница честности:** на полностью скомпрометированном endpoint защита контента ограничена — это
отражено в [anti-capture-matrix.md](anti-capture-matrix.md) («фундаментально недостижимо»).

#### D. Инсайдер-админ (привилегированный доступ)
**Цели:** злоупотребление доступом к ПДн/записям/медиа, заметание следов, эскалация.
**Векторы:** чтение чужих данных вне служебной необходимости, отключение audit, подмена статусов
посещаемости, доступ к at-rest ключам, включение скрытой записи.
**Контроли:**
- **Разделение ролей (D-007):** выделенный **Security Officer (аудитор)** — read-only к audit-логам,
  не совпадает с Admin/HR. Принцип: тот, кто администрирует, не контролирует сам себя.
- **Append-only audit:** записи audit-лога не редактируются и не удаляются из приложения;
  привилегированные действия (смена политик, доступ к записям, экспорт ПДн) логируются обязательно.
- **RBAC + department-scoping:** Manager видит только свою ветку иерархии (рекурсия `parent_id`);
  доступ всегда `org_id`-scoped — даже админ не выходит за границу тенанта по умолчанию.
- **Запись по политике (D-009):** включение записи — событие в audit с автором и обоснованием;
  «скрытой» записи на уровне процесса быть не должно (участники видят watermark/индикацию).
- **Секреты вне приложения:** at-rest ключи и LiveKit-секреты в env/Vault, доступ к ним —
  инфраструктурный контроль (отдельный от прикладного админа).
**Остаточный риск (честно):** инсайдер с полным доступом к серверу/Vault/БД может многое. Полностью
устранить его на on-prem нельзя — митигируем разделением обязанностей, аудитом привилегированных
действий и тем, что доступ к инфраструктуре уже = доверенная зона ведомства.

### 2.3 Out of scope / остаточные риски (управление ожиданиями)
- **Сервер видит медиа** — это сознательное решение (D-010): E2EE off, иначе серверный ML невозможен.
  «Защищённый канал» = да; «нулевое доверие к серверу» = нет. Доверяем on-prem инфраструктуре ведомства.
- **Вторая физическая камера** на экран — не блокируется ничем.
- **Звукозапись** (микрофон/loopback) — не блокируется нигде → только forensic-watermark + трассировка.
- **Web-захват** OS-средствами — поэтому видео в web отсутствует (D-001).
- **Rooted/jailbroken** устройства снижают эффективность enforce → детект + risk-scoring, не гарантия.

## 3. Security-контроли по слоям

### 3.1 Аутентификация (D-006)
- Внутренние учётки; пароли — **Argon2id**. Админ/HR заводит сотрудников (нет открытой регистрации).
- **TOTP 2FA** обязательна (`nimble_totp`): enrollment при создании, вход = пароль + TOTP.
- **Rate-limit** на вход и чувствительные endpoint; защита от brute-force/credential-stuffing.
- **Session-timeout**, инвалидация сессий; audit всех входов (успех/неуспех, IP, устройство, гео).
- **Hook для гос-SSO** (OneID/E-IMZO) заложен на будущее — не зависим от гос-IdP на старте.

### 3.2 Авторизация / RBAC (D-007)
- Роли: **SuperAdmin, Admin/HR, Manager, Employee + Security Officer (аудитор, read-only audit)**.
- **Department-scoping** по гос-иерархии (ведомство→управление→отдел через `parent_id`, рекурсивный
  обход): Manager видит только свою команду/ветку.
- Все запросы **`org_id`-scoped** (D-005): single-tenant сейчас, изоляция с дня 1 → multi-tenant без переписывания.
- Разделение обязанностей: аудитор ≠ администратор (защита от актора D).

### 3.3 Audit (D-014, foundation overkill)
- **Сквозной append-only audit-log**: входы, изменения политик, доступ к записям/ПДн, экспорт,
  административные действия, включение записи (D-009), результаты гео/VPN-проверок.
- Записи не редактируются/не удаляются из приложения; целостность = доказуемость для B2G.
- Доступ к audit — отдельная роль Security Officer (read-only).

### 3.4 Шифрование (D-010) — детали в [encryption.md](encryption.md)
- **Медиа in-transit:** DTLS-SRTP (hop-by-hop; SFU — доверенная точка, декодирует in-memory для ML).
- **At-rest:** диск-шифрование Postgres + **app-level AES-256** для фото-эталонов и записей.
- **Control-plane** (сигналинг/JSON API/LiveView/webhooks): **TLS 1.2+**.
- **E2EE off** — несовместимо с серверным ML (см. [encryption.md](encryption.md) и D-010).
- **Секреты** (LiveKit key/secret, JWT, at-rest ключи, DB-креды) — env/Vault, **не в git**.

### 3.5 Сеть (D-012)
- **On-prem** Kubernetes (2-node), ArgoCD (GitOps). Нет публичного облака для медиа/данных.
- LiveKit: **host-networking** (требование WebRTC), 1 SFU/нода, coTURN, Redis.
- **VPN/proxy-детект** и **гео-блок**: MaxMind GeoIP2 (Anonymous IP + Country) через Elixir `locus` —
  **self-host, без внешних API** («Max Data Security Private»).
- **Webhooks**: HMAC-SHA256 подпись тела (читать raw body до Plug-парсинга), проверка `Authorization`.
- Минимизация внешней экспозиции; сегментация; секреты инфраструктуры вне прикладного контура.

### 3.6 Анти-захват контента (D-001, D-013) — детали в [anti-capture-matrix.md](anti-capture-matrix.md)
- Видео — **только нативный клиент (Tauri)**; web несёт только управление (самая дырявая платформа
  убрана из контура видео).
- 6-слойная стратегия: **enforce** (Win/Android) · **detect** (mac/iOS) · **видимый watermark** ·
  **forensic аудио-watermark** · **политика/юр.уведомление** · **мониторинг/risk-scoring**.
