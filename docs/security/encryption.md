## 1. Краткая сводка

| Слой | Защита | Алгоритм/протокол | Доверенная точка |
|------|--------|-------------------|------------------|
| **Медиа in-transit** (A/V поток) | ✅ Шифруется hop-by-hop | DTLS-SRTP | SFU (LiveKit) декодирует in-memory |
| **At-rest — Postgres** (общие данные) | ✅ Диск-шифрование | Disk/volume encryption (LUKS / storage-class) | Инфраструктура |
| **At-rest — фото-эталоны и записи** | ✅ App-level | **AES-256** (GCM, прикладной слой) | Приложение + KMS/Vault ключи |

**Главный принцип (D-010):** «защищённый канал» = да; «нулевое доверие к серверу» = нет.
Это **employer-monitoring** на доверенной on-prem инфраструктуре ведомства, а не zero-trust-мессенджер.

## 2. Медиа in-transit — DTLS-SRTP (hop-by-hop)

### Что это
Медиа (видео/аудио) шифруется **по сегментам**: клиент ↔ SFU и SFU ↔ клиент, каждый сегмент —
отдельное DTLS-SRTP-шифрование (стандарт WebRTC). LiveKit-SFU расшифровывает поток **в памяти**,
ретранслирует подписчикам и при необходимости отдаёт кадры серверному ML (Egress/Agents).

```
Клиент A ──DTLS-SRTP──► [ LiveKit SFU: decode in-memory ] ──DTLS-SRTP──► Клиент B
                              │
                              └──► ML (face-match / liveness / deepfake) — D-011
                              └──► Egress (опц. запись по политике) — D-009
```

### Почему НЕ E2EE (ключевое решение D-010)
Настоящий E2EE (LiveKit insertable streams) шифрует медиа ключом, известным **только участникам** —
SFU видит «opaque bytes» и **не может декодировать**. Прямое следствие (разведка
[livekit-selfhost-e2ee.md](../research/livekit-selfhost-e2ee.md) §2):

- **LiveKit Agents не умеют декодировать E2EE-треки** → face-match / liveness / анти-DeepFake **невозможны**.
- **Egress несовместим с E2EE** → серверная запись (D-009) невозможна.

Требование ТЗ — серверный ML для контроля подлинности участников (анти-DeepFake, D-011). E2EE прямо
противоречит этому требованию. **Вердикт: E2EE off**, сервер — доверенная точка декодирования.

**Граница честности:** компания/ведомство доверяет своим on-prem серверам; медиа защищено в канале
от внешнего перехвата (MITM), но не от самого сервера — это сознательный и необходимый компромисс
для employer-monitoring. Отражено в модели угроз ([SECURITY.md](SECURITY.md) §2.3, актор D).

### Что это даёт / не даёт
- ✅ Защита от внешнего перехвата канала (MITM на сети).
- ✅ Совместимость с серверным ML и серверной записью.
- ❌ Не защищает медиа от доверенного сервера (by design).
- ❌ Не защищает от захвата экрана/звука на стороне клиента → отдельный контур
  ([anti-capture-matrix.md](anti-capture-matrix.md)).

## 3. At-rest — данные в покое

Два уровня (defense-in-depth):

### 3.1 Диск-шифрование Postgres
Общие данные БД (учётки-хеши, журналы посещаемости, audit, метаданные) на зашифрованном
volume/диске (LUKS или шифрующий storage-class K8s). Защита от физической кражи носителя.

### 3.2 App-level AES-256 для чувствительного контента
**Фото-эталоны (биометрия лица — ПДн) и записи совещаний** шифруются на **прикладном уровне
AES-256** (рекомендуется AES-256-GCM — аутентифицированное шифрование) до записи в хранилище:

- **Фото-эталоны** сотрудников (ФИО+Фото для face-match, D-011) — повышенная чувствительность как
  биометрические ПДн (закон РУз о ПДн — см. [compliance.md](compliance.md)).
- **Записи совещаний** (D-009): Egress пишет в S3-совместимое хранилище, файлы шифруются AES-256,
  доступ — только через RBAC + audit.

Зачем app-level поверх диск-шифрования: диск-шифрование защищает от кражи носителя, но не от доступа
через работающую БД/хранилище. App-level криптография ограничивает доступ к открытому контенту
теми компонентами, у которых есть ключ (envelope encryption через KMS/Vault).

## 4. Control-plane — TLS 1.2+

Весь не-медиа трафик шифруется **TLS 1.2+** (рекомендуется TLS 1.3 где доступно):

| Канал | Протокол | Примечание |
|-------|----------|------------|
| Web-админка (LiveView) | HTTPS/WSS | без видео (D-001) |
| JSON API для Tauri-клиента | HTTPS | выдача JWT, управление |
| LiveKit сигналинг | WSS | установка сессии |
| Webhooks LiveKit → Phoenix | HTTPS + **HMAC-SHA256** | подпись тела (raw body до Plug-парсинга), проверка `Authorization` |
| RoomService REST/Twirp (Phoenix → LiveKit) | HTTPS | через Finch |

JWT для LiveKit — **HS256** (симметричный ключ key/secret), короткоживущие, выдаются per-join
([livekit-selfhost-e2ee.md](../research/livekit-selfhost-e2ee.md) §3).

## 5. Управление ключами и секретами

> **Закон проекта: секреты НЕ в git.** ([SECURITY.md](SECURITY.md), D-014).

| Секрет | Назначение | Хранение |
|--------|-----------|----------|
| LiveKit **API key / secret** | подпись JWT (HS256), RoomService | env / Vault |
| **At-rest ключи** (AES-256 для фото/записей) | шифрование контента | KMS / Vault (envelope), **не на клиенте** |
| **DB-креды** | доступ Postgres | env / Vault (runtime-config) |
| TLS-сертификаты / приватные ключи | TLS 1.2+ | secret-store K8s / Vault |
| Webhook HMAC-секрет | проверка webhooks | env / Vault |
| Session/cookie signing keys | подпись сессий Phoenix | env / Vault |

**Практики:**
- Phoenix — **runtime-config** (секреты читаются из env/Vault при старте релиза, не в коде/git).
- K8s-секреты в GitOps — через sealed-secrets/Vault, **не plaintext в манифестах**.
- **Клиент (Tauri) не хранит долгоживущих ключей** — только короткоживущие per-join JWT (минимизация
  ущерба при компрометации устройства, актор C в [SECURITY.md](SECURITY.md)).
- Ротация ключей и сертификатов — процедурно (детали — открытый вопрос, зависит от инфра-политики).

**Открытый вопрос (заказчик):** требования к СКЗИ/сертифицированной криптографии для гос-сегмента РУз
(возможна обязательность сертифицированных алгоритмов/модулей вместо/вместе с AES-256/TLS) —
**ТРЕБУЕТ УТОЧНЕНИЯ У ЗАКАЗЧИКА**, см. [compliance.md](compliance.md).

## 6. Связь с другими решениями
- **D-009** (серверная запись) — записи шифруются at-rest AES-256, RBAC + audit.
- **D-011** (ML-стек) — требует декодируемого медиа на сервере → причина E2EE off.
- **D-012** (Net/Geo) — control-plane под TLS, гео-данные self-host.
- **D-013/D-001** (анти-захват) — ортогонально шифрованию: защищает контент на endpoint, не канал.
