## 1. Контекст комплаенса

Заказчик — государственное ведомство Республики Узбекистан. Система обрабатывает **ПДн госслужащих**
(включая **биометрию лица** — фото-эталоны для face-match), **записи гос-совещаний** и **поведенческие
данные** (журналы посещаемости). Для B2G в РУз ожидаемо применимы несколько регуляторных контуров,
перечисленных ниже. **Финальный перечень и конкретные требования формализуются совместно с
юристами/комплаенс-офицером заказчика** — это вход в проект, а не наше предположение.

## 2. Вероятно применимые регуляторные контуры

> Перечень — **ориентир для разговора с заказчиком**. Каждый пункт требует подтверждения применимости
> и конкретных версий/редакций нормативки.

### 2.1 Защита персональных данных (закон РУз о ПДн)
**Что:** обработка ПДн госслужащих, включая **биометрические данные** (фото лица). В РУз действует
законодательство о персональных данных, устанавливающее требования к обработке, хранению, защите и,
как правило, **локализации/размещению ПДн граждан на территории страны**.
**Как уже учтено в архитектуре:**
- On-prem развёртывание (D-003, D-012) — данные не покидают инфраструктуру ведомства.
- App-level **AES-256** для фото-эталонов (биометрия) ([encryption.md](encryption.md) §3.2).
- RBAC + `org_id`-изоляция + audit доступа к ПДн (D-007, D-014).
**ТРЕБУЕТ УТОЧНЕНИЯ У ЗАКАЗЧИКА:**
- ☐ Точное наименование/редакция закона РУз о ПДн и применимых подзаконных актов.
- ☐ Требования к **локализации ПДн** (обязательное размещение на территории РУз / в гос-сегменте).
- ☐ Особый режим для **биометрических ПДн** (фото лица): согласие, сроки хранения, спец-защита.
- ☐ Обязанность регистрации базы ПДн в гос-реестре / уведомления регулятора.
- ☐ Права субъектов ПДн (доступ/удаление) и сроки реагирования.

### 2.2 Национальные стандарты ИБ (O'zDSt)
**Что:** в РУз действует система гос-стандартов **O'zDSt**, в т.ч. в области информационной безопасности
(возможны адаптации ISO/IEC 27001 и др.). Для гос-систем соответствие может быть обязательным.
**ТРЕБУЕТ УТОЧНЕНИЯ У ЗАКАЗЧИКА:**
- ☐ Конкретные применимые номера **O'zDSt** по ИБ (номера/редакции — **не выдумываем**, запросить у заказчика).
- ☐ Обязательность сертификации/аттестации системы по этим стандартам.
- ☐ Требования к классу защищённости гос-информационной системы.

### 2.3 Криптография / СКЗИ (госэкспертиза)
**Что:** применение средств криптографической защиты информации (СКЗИ) в гос-сегменте РУз может
требовать использования **сертифицированных/одобренных** алгоритмов и модулей, прохождения
**государственной экспертизы**, лицензирования криптодеятельности.
**Как сейчас в архитектуре** ([encryption.md](encryption.md)): TLS 1.2+, DTLS-SRTP, AES-256, Argon2id —
индустриальные стандарты, **но не подтверждена их допустимость для гос-сегмента РУз**.
**ТРЕБУЕТ УТОЧНЕНИЯ У ЗАКАЗЧИКА:**
- ☐ Обязательны ли **сертифицированные СКЗИ** (конкретный перечень одобренных алгоритмов/модулей) — **не выдумываем**.
- ☐ Допустимы ли AES-256 / TLS / DTLS-SRTP или нужна замена/дополнение национальными СКЗИ.
- ☐ Требуется ли **госэкспертиза** криптографической подсистемы и кто её проводит.
- ☐ Лицензионные требования к разработке/эксплуатации СКЗИ.

### 2.4 Размещение данных / суверенитет (on-prem)
**Что:** для гос-данных типична обязательность размещения в национальном/ведомственном дата-центре,
запрет на иностранное облако, требования к физической защите.
**Как уже учтено:** **on-prem K8s** (2-node, D-003/ARCHITECTURE.md), self-host LiveKit, self-host
GeoIP без внешних API (D-012) — **«Max Data Security Private»**, никаких внешних SaaS в контуре данных.
**ТРЕБУЕТ УТОЧНЕНИЯ У ЗАКАЗЧИКА:**
- ☐ Требования к **расположению ЦОД** (конкретная площадка/сертификация ЦОД).
- ☐ Допустимость текущей on-prem K8s-инфраструктуры (или нужен аттестованный гос-ЦОД).
- ☐ Требования к физической безопасности и доступу к серверам.

### 2.5 Аудит, протоколирование, хранение
**Что:** гос-системы обычно требуют неизменяемого журналирования действий, сроков хранения,
возможности расследования инцидентов.
**Как уже учтено:** сквозной **append-only audit-log**, выделенная роль **Security Officer**
(read-only аудитор), логирование привилегированных действий ([SECURITY.md](SECURITY.md) §3.3, D-014).
**ТРЕБУЕТ УТОЧНЕНИЯ У ЗАКАЗЧИКА:**
- ☐ Обязательные **сроки хранения** audit-логов, записей совещаний, ПДн.
- ☐ Требования к формату/экспорту журналов для проверяющих органов.
- ☐ Регламент реагирования на инциденты ИБ и уведомления регулятора.

### 2.6 Идентификация / гос-SSO
**Что:** гос-системы могут требовать интеграции с национальными системами идентификации
(напр. OneID, E-IMZO/ЭЦП).
**Как уже учтено:** **hook для гос-SSO заложен** (D-006) — старт на внутренних учётках + 2FA,
интеграция OneID/E-IMZO активируется по требованию.
**ТРЕБУЕТ УТОЧНЕНИЯ У ЗАКАЗЧИКА:**
- ☐ Обязательна ли интеграция с **OneID / E-IMZO** и на каком этапе.
- ☐ Требования к ЭЦП (подписание протоколов совещаний, действий).

## 3. Как архитектура уже работает на комплаенс

| Требование (вероятное) | Уже заложено | Решение |
|------------------------|--------------|---------|
| Локализация / суверенитет данных | ✅ | On-prem K8s, self-host LiveKit, self-host GeoIP (D-003, D-012) |
| Защита ПДн / биометрии | ✅ (частично) | AES-256 фото, RBAC, `org_id`-изоляция, audit (D-007, D-010, D-014) |
| Неизменяемый аудит | ✅ | Append-only audit-log + Security Officer (D-014, D-007) |
| Шифрование в покое и в канале | ✅ | AES-256 at-rest, TLS 1.2+, DTLS-SRTP (D-010) |
| Разделение обязанностей | ✅ | RBAC 4+1, аудитор ≠ админ (D-007) |
| Гос-SSO / ЭЦП | ◐ hook | Заложен hook OneID/E-IMZO (D-006), активация по требованию |
| Сертифицированные СКЗИ | ❓ открыто | **Требует уточнения** — допустимость текущей криптографии не подтверждена |
| Соответствие O'zDSt по ИБ | ❓ открыто | **Требует уточнения** — конкретные стандарты не определены |

Легенда: ✅ заложено · ◐ заложен задел/hook · ❓ открытый вопрос к заказчику.

## 5. Дисклеймер

Этот документ — **рабочий каркас для сбора требований**, не юридическое заключение и не подтверждение
соответствия. Все пункты с пометкой **«ТРЕБУЕТ УТОЧНЕНИЯ У ЗАКАЗЧИКА»** обязательны к закрытию до
финализации архитектуры безопасности. Конкретные нормы законодательства РУз, номера O'zDSt и требования
к СКЗИ **подлежат подтверждению у заказчика и его юридической/комплаенс-службы** — в этом документе они
намеренно **не утверждаются по памяти**, чтобы не внести ложную конкретику в B2G-проект.

> По мере получения ответов — обновлять §2-3 и заводить ADR (D-015+) на принятые комплаенс-решения.
