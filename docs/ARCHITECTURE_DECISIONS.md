# Architecture Decision Records (ADR) — Security Video Conference

> Формат: D-numbered. Каждое решение — контекст, выбор, обоснование, последствия.
> Зафиксировано на сессии брейншторма 2026-06-05 (команда + Клауди). Основания — разведка 4 отрядов (`docs/research/`).

---

## D-001: Платформа видео — нативный клиент, web только управление
**Контекст:** ТЗ требует enforce анти-захвата; в браузере это невозможно.
**Решение:** Видеоконференция — только нативный клиент (desktop/mobile). Web = панель управления (админка, журналы, планирование) БЕЗ видео.
**Обоснование:** убирает самую дырявую платформу из контура видео; фокусирует security-усилия туда, где enforce реален (Win/Android). См. `docs/research/anti-capture-platforms.md`.
**Последствия:** E5 упрощается; web-приложение не несёт WebRTC.

## D-002: Desktop-клиент — Tauri
**Контекст:** Windows-доминирование, max-security, LiveKit, Rust-экспертиза.
**Решение:** **Tauri** (Rust shell + WebView2 + LiveKit JS). Отвергнуты: Electron (RISKY), нативный Qt/.NET (NO-GO), Flutter Desktop (NOT READY).
**Обоснование:** `setContentProtected`→нативный Win32; LiveKit JS в WebView2; Rust-бэкенд для детекта/TPM/kiosk; 10× легче Electron. Electron анти-захват #47834 сломан на ~30-40% Windows. У LiveKit нет нативного SDK. См. `docs/research/desktop-framework.md`.
**Последствия:** PoC-спайк LiveKit+WebView2 обязателен (MODERATE risk).

## D-003: SFU — LiveKit self-host
**Решение:** LiveKit, self-host на on-prem K8s. **Обоснование:** open-source, E2EE-опция, SDK для всех платформ, Elixir SDK (`livekitex`), self-host под «Max Data Security». **Последствия:** host-networking, 1 SFU/нода, Redis, coTURN.

## D-004: Backend-ядро — Elixir/Phoenix umbrella
**Решение:** Phoenix umbrella — `svc` (core: contexts + Repo + schemas) + `svc_web` (LiveView/API). **Обоснование:** совпадает со стеком; Presence=журнал посещаемости из коробки; Channels=сигналинг; PubSub=уведомления; чёткие границы под рост; «foundation overkill». **Последствия:** umbrella-церемония оправдана масштабом.

## D-005: Тенантность — single + задел на multi
**Решение:** Single-tenant, но `org_id` во всех таблицах + изоляция с дня 1. **Обоснование:** B2G (одно ведомство сейчас), но multi-ведомства/продажа без переписывания. **Последствия:** `org_id`-scoping во всех запросах.

## D-006: Auth — внутренние учётки + 2FA
**Решение:** Внутренние учётки (Argon2id) + TOTP 2FA; админ заводит сотрудников. **Обоснование:** автономность, без зависимости от гос-IdP на старте; быстрый E0.
**Обновление 2026-06-05:** ❌ OneID/E-IMZO интеграция (гос-SSO) **исключена из роадмапа** — не планируется. Внутренних учёток + 2FA достаточно; зависимость от гос-IdP не вводим.

## D-007: RBAC — 4+1 роли + department-scoping
**Решение:** SuperAdmin, Admin/HR, Manager, Employee + Security Officer (аудитор). Scoping по гос-иерархии (ведомство→управление→отдел через `parent_id`). **Обоснование:** «контроль сотрудников» требует иерархии (Manager видит свою команду). Granular custom-роли — эволюция. **Последствия:** рекурсивный обход иерархии для видимости.

## D-008: Посещаемость — гибрид
**Решение:** Запланированные встречи (ростер + авто-статусы present/late/absent/left_early) + ad-hoc (факт-лог без absent). **Обоснование:** «кто отсутствовал» требует ожидаемого списка; ad-hoc покрывает спонтанные созвоны. **Последствия:** Oban-джоба вычисляет absent при завершении встречи.

## D-009: Серверная запись — опционально по политике
**Решение:** По умолчанию off; организатор/политика включает per-meeting (Egress, шифр. at-rest, RBAC, audit). **Обоснование:** гос может требовать архив протокола ИЛИ запрещать — гибкость. Ортогонально «запрету записи участниками». **Последствия:** тот же Egress кормит ML (E6).

## D-010: Шифрование медиа — hop-by-hop (E2EE off)
**Контекст:** настоящий E2EE ⊥ серверный ML (анти-DeepFake).
**Решение:** E2EE **off**; hop-by-hop DTLS-SRTP (сервер доверенная точка) + at-rest AES-256 + TLS. **Обоснование:** для employer-monitoring сервер должен видеть кадры для ML; компания доверяет своим on-prem серверам. См. `docs/research/livekit-selfhost-e2ee.md`. **Последствия:** «защищённый канал» = да, но не «нулевое доверие к серверу».

## D-011: ML-стек (E6) — Python + Rust гибрид
**Решение:** Python (FastAPI, модели) + Rust (`ort`/ONNX, GPU-инференс). Face-match=InsightFace/ArcFace (приоритет, ~98%), liveness=MiniFASNet, deepfake=R&D-трек (~78%, risk-flag). **Обоснование:** 99% моделей в PyTorch (не чистый Rust); Rust для latency. См. `docs/research/ml-stack.md`. **Последствия:** deepfake НЕ продавать как 100%.

## D-012: Net/Geo (E7) — MaxMind + Locus
**Решение:** VPN-детект + гео-блок через MaxMind GeoIP2 (Anonymous IP + Country) + Elixir `locus` (self-host, без внешних API). GPS — mobile (фаза 2). **Обоснование:** «Max Data Security Private» → без внешних API. **Последствия:** GPS-функции зависят от mobile-клиента.

## D-013: Anti-capture (E5) — слоистая стратегия
**Решение:** enforce Win (`setContentProtected`)/Android (FLAG_SECURE); detect mac/iOS; видимый watermark + forensic аудио-watermark; политика. **Обоснование:** enforce невозможен везде; аудио не запретить нигде → трассировка. См. `docs/research/anti-capture-platforms.md`. **Последствия:** честная коммуникация заказчику — не «100% запрет».

## D-014: Foundation overkill (закон проекта)
**Решение:** E0 строим по-максимуму с дня 1 (полный audit-log, шифрование, серьёзный RBAC, security-примитивы), не MVP-урезка. **Обоснование:** принцип проекта «На Foundation не бывает Overkill» — фундамент держит всё. **Последствия:** E0 — серьёзный объём, оправдан для B2G.

## D-015: E4 «CRM» = поручения + задачи (не sales-CRM)
**Решение (интервью 2026-06-05):** «CRM» в SVC = **система поручений руководства + задач сотрудникам** (единый task/assignment-модуль с Kanban-доской). Поручения часто рождаются из совещаний → связь с встречами (E1/E2). **Обращения граждан** — отдельный возможный модуль, отложен (требует уточнения у заказчика). **Обоснование:** для гос-ведомства «CRM» ≠ продажи; реальная потребность — контроль исполнения поручений и задач. **Последствия:** E4 строим как Tasks (поручение/задача: автор→исполнитель, дедлайн, приоритет, статус) + Kanban-UI + интеграция с E3-уведомлениями; обращения граждан — потом, по требованию.

## D-016: RBAC совещаний — организация по роли, видимость по участию
**Решение (заказчик, 2026-09-01):** организовывать совещания могут только `super_admin` и `manager` (`Meetings.can_organize?/1`); управление пользователями и назначение ролей — только `super_admin` (`UserLive.can_manage?/1`). Видимость совещания — **организатор ИЛИ приглашённый** (`Meetings.visible_query/2`), без исключения для `super_admin`. Кого можно пригласить — по рангу: `@role_rank` (super_admin 4 · admin_hr 3 · manager 2 · security_officer/employee 1), руководитель прикрепляет равных себе и ниже (`Authz.assignable_users/1`, проверка дублируется на сервере в `create`).
**Обоснование:** заказчик прямо потребовал, чтобы главный администратор мог делать всё (создавать совещания, рассылать документы), **но не видел закрытые совещания других руководителей** — иначе «секретное совещание» теряет смысл в гос-структуре. Ранг вместо явного списка ролей — чтобы новая роль не требовала правок в проверках.
**Последствия:** `super_admin` — не «видит всё»; для расследований нужен отдельный явный путь (audit-log), а не тихий доступ к содержимому. Регрессионный тест на невидимость закреплён в тест-сьюте.

## D-017: Обязательное обновление мобильного клиента (OTA, без сторов)
**Решение (заказчик, 2026-09-09):** `version.json` на лендинге несёт `minVersionCode` (Android) и `ios.minBuild`. Клиент проверяет версию **до** авторизации; если установленная ниже минимальной — показывается блокирующий экран, и ничего больше. Android скачивает APK внутри приложения и открывает системный установщик (`REQUEST_INSTALL_PACKAGES` + FileProvider) — **без браузера и без Play Market**; кнопка «Назад» заблокирована (`BackHandler {}`). iOS блокирует так же, но установить сам не может (запрет Apple) — ведёт на страницу установки.
**Обоснование:** заказчик потребовал, чтобы устаревшие клиенты не работали. Для B2G это ещё и требование безопасности: старый клиент может не иметь актуальных анти-захват-ограничений и не должен подключаться к закрытым совещаниям.
**Последствия:** (1) проверка **fail-open** — при недоступной сети приложение не блокируется, иначе клиент «кирпичится» без сервера; (2) обновление в приложении требует, чтобы подпись APK совпадала — переход на новый keystore разорвёт цепочку обновлений у установленных пользователей; (3) блокировка действует **только начиная с версии, где есть этот код** (v0.5.0) — на ≤ v0.4.3 обновление выглядит как обычный диалог.

## D-018: Детект рекордеров — сигнатуры процессов, приоритет точности над полнотой
**Контекст (S36, 2026-09-11):** `setContentProtected` даёт настоящий ENFORCE только на Windows; macOS 15+ обходится через ScreenCaptureKit, Linux — no-op (D-013). Нужен второй слой: детект.
**Решение:** Rust-модуль в Tauri перечисляет процессы (`sysinfo`) и сверяет с таблицей сигнатур. Матчинг **двухуровневый**: `exact` по нормализованному имени (basename, без `.exe`, lowercase) для коротких и общих слов; `contains` — только для характерных токенов (`bandicam`, `simplescreenrecorder`, `screentogif`). Общие инструменты вроде `ffmpeg` в таблицу **не входят**. Средства удалённого доступа (AnyDesk/RustDesk/TeamViewer) пишутся тем же `kind: recorder_detected`, но с `detail.category = "remote_access"`.
**Обоснование:** политика встречи может быть `eject` (D-011/S30) — то есть ложное срабатывание **выкидывает невиновного участника из совещания**. Поэтому цена false positive выше цены пропуска: `action`→`transaction`, `peek`→`peekaboo`, `loom`→`bloom` при наивном substring дали бы именно это. `ffmpeg` запускается в фоне десятками легитимных программ. Категория `remote_access` отделена, потому что угроза та же (кадры покидают машину), а сценарий и разговор с пользователем — разные.
**Последствия:** (1) детект **не является гарантией** — переименованный бинарник, отсутствующий в таблице инструмент и съёмка экрана телефоном не ловятся; формулировка «снижение риска, а не гарантия» зафиксирована в `docs/security/anti-capture-matrix.md` и не должна смягчаться в маркетинге (см. D-013); (2) таблица сигнатур требует сопровождения — при появлении нового популярного рекордера её нужно дополнять; (3) проверена на Linux, на Windows-парке имена процессов иные — нужен отдельный прогон; (4) дедуп по паре (имя, pid): закрытый и заново открытый рекордер считается новым событием — это намеренно, повторный запуск во время закрытого совещания значим.

## D-019: Встроенный помощник — без LLM, база знаний на сервере
**Контекст (S37, 2026-09-13):** заказчик попросил AI-помощника внизу экрана, который объясняет, как пользоваться системой.
**Решение:** помощник работает **без языковой модели** — вопрос сопоставляется с серверной базой знаний по ключевым словам (`Svc.Assistant`), ответы лежат в коде на uz/ru/en. Контент и поиск — **на сервере**, все три клиента (веб, Android, Tauri) ходят в один REST API `/api/assistant/*`.
**Обоснование:** (1) продукт продаётся как полностью self-hosted, «без зависимости от зарубежного облака» — отправка вопросов госслужащих во внешний LLM API противоречила бы собственному обещанию на первом слайде презентации и духу D-010; (2) self-hosted модель требует GPU, а это уже заблокированный по бюджету пункт (E6); (3) для задачи «как создать совещание» детерминированный ответ из базы точнее генеративного и не может выдумать несуществующую функцию — для B2G ложное обещание хуже отсутствия ответа; (4) справка в трёх клиентских копиях разъехалась бы после первого же изменения продукта, а обновить Android у всех сразу нельзя.
**Последствия:** (1) помощник отвечает только на то, что есть в базе — при неуверенном совпадении честно говорит «не понял» и предлагает темы; (2) база требует сопровождения: новая функция → новая запись, иначе справка устаревает; (3) сопоставление учитывает морфологию узбекского и русского (общий префикс ≥ 4 при «хвосте» ≤ 5) и отсеивает стоп-слова — без этого «как мне сделать» матчилось бы со всем подряд; (4) записи фильтруются по роли, а при попадании в недоступную роль возвращается `restricted` с перечнем ролей — «спрятать» ответ значило бы показать сотруднику случайный соседний; (5) **путь к апгрейду открыт**: за тем же API можно позже включить self-hosted модель, клиентов менять не придётся.

## D-020: Уведомление об обновлении приложения — автоматически, по опубликованному манифесту
**Контекст (2026-09-13, требование заказчика):** «когда мы что-то меняем, уведомление об обновлении должно уходить автоматически». OTA-механизм D-017 срабатывает, только когда человек **открывает** приложение, а сборки ≤ v0.4.3 блокироваться не умеют вовсе. Серверное уведомление доходит до любой установки v0.4.0+: `NotifyWorker` на телефоне раз в 15 минут забирает `/api/notifications` и показывает системное уведомление даже при закрытом приложении.
**Решение:** сервер сам раз в 10 минут (Oban Cron) читает опубликованный манифест — тот же `version.json`, что читают клиенты. Если Android `versionCode` в нём новее всего, что уже объявлено, в `app_release_announcements` вставляется одна строка (уникальный индекс `platform + version_code`), и всем активным пользователям уходит уведомление `kind: :update`. Триггер — сам манифест, а не скрипт релиза.
**Обоснование:** (1) не зависит от способа релиза — скрипт, загрузка через File Browser, ручная правка: источник правды тот же файл, которому уже доверяют клиенты; (2) ровно один раз — уникальный индекс не даст разослать повторно ни при параллельных запусках cron, ни при повторном релизе той же версии; (3) доходит до тех, кто приложение не открывает, и до старых сборок, которые не умеют блокироваться; (4) выключено, пока не задан `APP_RELEASE_MANIFEST_URL`, — локальная разработка, CI и другие развёртывания не рассылают уведомлений своим пользователям.
**Последствия:** (1) задержка до ~25 минут (10 мин cron + 15 мин `NotifyWorker`) — для обновлений приемлемо; (2) `app_release_announcements` — таблица развёртывания **без `org_id`**, осознанное исключение из D-005: APK принадлежит серверу, а не организации — все организации на нём получают один и тот же APK; (3) iOS пока не объявляется — сборка 1 помечена «готовится» и не распространяется; колонка `platform` уже есть, включение iOS — изменение кода без миграции; (4) уведомление получают все активные пользователи, включая тех, кто работает только в веб-панели, — текст прямо называет Android-приложение, при росте веб-only ролей пересмотреть; (5) объявление v0.5.1 было отправлено вручную 2026-09-13 и при деплое занесено в таблицу, чтобы первый запуск cron его не повторил.
